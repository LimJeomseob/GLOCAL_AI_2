# [검수용] 시스템 점검 회차 — 가상자료로 보는 선발 이후 운영 과정

> 대상: 「글로컬 AI 동행」 포털 — AI 활용 연구모임(트랙 B) 검수자·운영 담당자
> 입력 스크립트: `scripts/seed_system_check_round.sql` · 삭제 스크립트: `scripts/reset_system_check_round.sql`
> 모든 인물·연락처·이메일·내용은 **가상**입니다. 실제 신청자 정보는 한 건도 쓰지 않았습니다.

---

## 1. 범위

**선발 이후 과정만** 시연합니다.

```
선발 안내 → 전문가 배정·팀별 최종 일정 공지 → 코칭 일정 조율 → 회의록 → 결과보고서 → 이수확정
```

신청·계획서 심사 단계는 시연하지 않습니다. 다만 선발 이후 화면에 점수·순위와 계획서가 보여야 하므로,
계획서 제출 이력과 심사 점수(3인)만 최소한으로 채웠습니다.

| 항목 | 값 |
|---|---|
| 회차 | `2026` / `0학기(시스템점검)` — 「[시스템 점검] AI 활용 연구모임 운영 검수 회차 (가상자료)」 |
| 공개 여부 | `is_active = false` → 사업안내·신청 화면은 계속 2학기 회차만 표시 |
| 가상 일정 | 운영 7.20.~8.28. · 결과보고 마감 8.28. |
| 선발 팀 | 5팀 (`SG-2026-0-001`~`005`) · 전문가 2명 (`EX-2026-0-001`~`002`) |
| 가상 인물 표식 | 이름 「○점검」, 연락처 `010-0000-####`, 이메일 `@example.com`(실제 수신자 없는 예약 도메인) |

### 실운영과의 격리

- 관리자 화면의 회차 선택 기본값은 계속 「2학기」이고, 점검 회차는 그 아래에 있습니다.
- 「안내 발송」 탭은 전체 큐를 보여 주므로, 가상 행은 제목 앞에 **`[점검·가상]`**을 붙였습니다.
- 삭제 스크립트는 점검 회차 자료만 지웁니다.

---

## 2. 실행·삭제

1. Supabase 대시보드 → **SQL Editor**
2. `scripts/seed_system_check_round.sql` 전체 실행 → 끝에 5팀 목록이 조회되면 완료
   (이미 입력되어 있으면 아무것도 하지 않고 안내만 출력)
3. 검수 종료 후 `scripts/reset_system_check_round.sql` 실행 (1번 블록으로 건수 확인 → 2번 블록 삭제)

## 4. 선발 이후 운영 과정 — 화면별 시연

### ① 선발 안내 (관리자 「안내 발송」)

- 상태가 **선발**로 바뀌면 선발 안내 메일이 제목·본문까지 작성된 채 큐에 쌓입니다.
- 관리자가 확인·수정한 뒤 승인 발송합니다(자동 발송 아님).
- 시연: 4팀 `심사결과` 행(대기) → 내용 확인 → **「취소」로 처리**(가상 수신자이므로 발송 금지).

### ② 전문가 배정·팀별 최종 일정 공지 (관리자 「연구모임 운영현황」·「연구모임 관리」)

| 관리자 작업 | 결과 화면 | 시연 팀 |
|---|---|---|
| 팀별 전문가 지정 | 대표자 「내 연구모임」·전문가 「배정 팀 확인」에 표시 | 1~5팀 |
| 팀별 최종 일정(기획·제작·환류 3단계) 입력·공개 | 대표자 「내 연구모임」에 표시 | 3팀(공개, 대표자가 직접 수정한 이력) |
| 공개 여부 끄기 | 대표자 화면에 표시 안 됨 | 4팀(비공개) → 공개로 바꿔 차이 확인 |

### ③ 코칭 일정 조율 (대표자 「내 연구모임」 ↔ 전문가 「배정 팀 확인」)

본인확인은 **성명 + 연락처**(3장 표)입니다.

```
팀 또는 전문가가 일정 제안 → 상대가 가능/불가 회신 → 확정 (회차당 확정 1건)
```

| 시연 | 계정 |
|---|---|
| 1차 제안에 **가능/불가 회신** | 전문가 한점검 → 5팀 |
| 2차 「가능」 건 **확정** | 대표자 박점검 → 3팀 |
| 조율 메모 확인·추가 | 3팀 (팀·전문가·관리자 메모 3건) |
| 3회 모두 확정된 완료 모습 | 1팀 |

### ④ 회의록 제출 (대표자 「회의록」)

- [서식 3] 회의록을 제출하면 관리자 「연구모임 운영현황」에 **n/3**으로 집계되고, 3회 미만은 강조됩니다.
- 선발 상태 팀이 첫 회의록을 내면 상태가 **운영중**으로 자동 전환됩니다.
- 시연: 4팀(0/3)으로 회의록 1건 제출 → 상태 전환 확인, 5팀(1/3)·3팀(2/3) 비교

### ⑤ 결과보고서 제출 (대표자 「결과보고서」)

- [서식 2] 1~5번 항목 + 산출물 링크(유형·드라이브 업로드 여부)를 제출하면 상태가 **결과보고서 제출**이 되고 이후 수정할 수 없습니다.
- 시연: 3팀 또는 5팀으로 제출, 2팀으로 제출 후 잠김 확인
- 관리자 「연구모임 운영현황」 산출물 아카이브: 유형 필터·CSV, 2팀 드라이브 미업로드 확인

### ⑥ 이수확정 (관리자 「연구모임 관리」 → 「안내 발송」)

- 관리자가 결과보고서 제출 팀의 상태를 **이수완료**로 바꾸면 이수확정 메일이 큐에 쌓입니다.
- 시연: 2팀을 이수완료로 변경 → 큐에 새 `[점검·가상]` 행 생성 확인 → 「취소」 처리. 1팀은 이미 완료된 모습 확인.

## 5. 주의사항 (확인된 동작)

| # | 내용 |
|---|---|
| 1 | 코칭 제안·회신·확정을 저장하면 **`[점검·가상]` 표식이 없는** 코칭 안내 메일이 큐에 쌓입니다. 수신자는 `@example.com`이므로 모두 「취소」 처리하십시오. |
| 2 | 회의록·결과보고서·코칭 저장은 날짜가 아니라 **상태**(선발·운영중)로 열립니다. 가상 운영기간(8.28.)이 지났어도 4·5·3팀으로 시연할 수 있고, 1·2팀은 보고서 제출 후라 잠겨 있습니다. |
| 3 | 점검 회차에서 「심사 확정」은 누르지 마십시오. 선발 상태인 4팀만 다시 순위가 매겨져 순위 표시가 달라집니다. |
| 4 | 검수 종료 후 반드시 `scripts/reset_system_check_round.sql`로 삭제하십시오. |
