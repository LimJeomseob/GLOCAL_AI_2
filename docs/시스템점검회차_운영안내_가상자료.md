# [검수용] 시스템 점검 회차 — 가상자료로 보는 연구모임 운영 전 과정

> 대상: 「글로컬 AI 동행」 포털 — AI 활용 연구모임(트랙 B) 검수자·운영 담당자
> 입력 스크립트: `scripts/seed_system_check_round.sql` · 삭제 스크립트: `scripts/reset_system_check_round.sql`
> 모든 인물·연락처·이메일·내용은 **가상**입니다. 실제 신청자 정보는 한 건도 쓰지 않았습니다.

---

## 1. 무엇을 넣는가

실제 2026학년도 2학기 회차와 **분리된 별도 회차**에, 운영 단계별 상태를 하나씩 가진 가상 연구모임 9팀과
교내 AI활용 전문가 3명을 넣습니다. 이 자료만으로 신청 → 심사 → 선발 → 운영 → 결과보고 → 이수확정의
전 과정을 실제 화면에서 시연할 수 있습니다.

| 항목 | 값 |
|---|---|
| 회차 | `2026` / `0학기(시스템점검)` — 「[시스템 점검] AI 활용 연구모임 운영 검수 회차 (가상자료)」 |
| 공개 여부 | `is_active = false` → 사업안내·신청 화면은 계속 2학기 회차만 표시 |
| 가상 일정 | 신청 7.1.~7.10. · 심사 마감 7.17. · 운영 7.20.~8.28. · 결과보고 마감 8.28. |
| 선발 규모 | 4팀 (실제 회차 10팀) · 팀 규모 3~5명 |
| 카테고리·심사기준 | 실제 2학기 회차에서 그대로 복사 (9개 지표 100점) |
| 접수번호 | 연구모임 `SG-2026-0-001`~`009`, 전문가 `EX-2026-0-001`~`003` (실제 `SG-2026-2-###`와 겹치지 않음) |
| 가상 인물 표식 | 이름이 모두 「○점검」, 연락처 `010-0000-####`, 이메일 `@example.com`(실제 수신자 없는 예약 도메인) |

### 실운영과의 격리

- 관리자 화면의 회차 선택 목록은 연도·학기 내림차순이라 **기본 선택은 계속 「2학기」**이고, 점검 회차는 그 아래에 뜹니다.
- 「안내 발송」 탭은 회차 구분 없이 전체 큐를 보여 줍니다. 가상 행은 제목 앞에 **`[점검·가상]`**이 붙어 있습니다.
- 삭제 스크립트는 점검 회차와 `[점검 가상자료]` 표식의 참여이력만 지웁니다.

## 2. 실행·삭제 방법

1. Supabase 대시보드 → **SQL Editor**
2. `scripts/seed_system_check_round.sql` 전체를 붙여넣고 실행
   - 끝에 9팀 목록이 조회되면 완료
   - 이미 점검 회차가 있으면 아무것도 하지 않고 안내만 출력합니다(중복 입력 방지)
3. 검수가 끝나면 `scripts/reset_system_check_round.sql` 실행
   - 1번 블록(건수 확인)을 먼저 보고 2번 블록(삭제)을 실행합니다
   - 연구모임을 지우면 참여자·계획서·심사·회의록·보고서·산출물·코칭·최종 일정·안내 큐가 함께 삭제됩니다

> 입력 과정: SQL Editor에는 관리자 로그인 정보가 없어 공개 신청과 똑같은 검사(신청 기간·팀 규모)를 받습니다.
> 그래서 입력하는 동안만 신청 기간을 "지금"으로 열었다가 끝에서 7월 가상 일정으로 되돌립니다.
> DB 트리거를 끄지 않았기 때문에 접수번호 채번, 참여자 수, 복수 학과 판정, 심사 총점, 안내 메일 큐는 실제 운영과 같은 경로로 만들어집니다.

## 4. 운영 전 과정 — 화면별 시연 순서

### ① 연구모임 신청 (신청자 → `/apply`)

| 신청자가 하는 일 | 시스템 동작 | 가상자료로 확인 |
|---|---|---|
| AI 윤리교육 영상 시청 + 8대 원칙 중 3개 이상 실천 다짐 작성 | 다짐 없이는 신청서로 진입 불가 | 모든 팀에 다짐 3건 입력됨(관리자 상세 팝업) |
| [서식 1] 신청서: 대표자·참여자 3~5명, 수준(초급~고급2) | 저장 시 접수번호 발급, 상태 **작성중(draft)** | 8팀 |
| 소속 입력 | 표기를 정규화해 **복수 학과**(동점 시 우선) 자동 판정 | 4팀: 「기계공학과」·「공과대학 기계공학과」·「경상국립대학교 기계공학과」 → 같은 학과로 판정 |

### ② 계획서 제출·심사 (신청자 `/plan` → 심사위원 「계획서 심사」)

| 단계 | 시스템 동작 | 가상자료로 확인 |
|---|---|---|
| 계획서 5개 항목 + 워크숍 희망일(1안·2안) 제출 | 상태 **제출완료(submitted)**, 팀 규모 3~5명 검사, 접수확인 메일이 큐에 쌓임 | 7팀 |
| 심사위원 3인 서면심사(9개 지표 100점) | 지표별 배점 상한을 DB가 검사하고 총점 자동 계산 | 6팀(2/3 제출) |
| 심사기준 1번(참여·이수 20점) | 특강 신청 이력 + 참여이력 대장에서 근거 자동 제시 | 1·2·3팀 대표자 |
| 선발 확정 | 3인 평균 → 순위 → 상위 N팀 선발, 동점 시 복수 학과 우선. 선발·미선발 메일이 큐에 쌓임 | 1~4팀 선발, 5팀 미선발 |

### ③ 운영 안내 (대표자 `/lookup` 「내 연구모임」, 전문가 `/expert-teams`)

본인확인은 **성명 + 연락처**입니다. 3장 표의 대표자·전문가 정보로 들어가 보면 됩니다.

| 화면 | 확인할 내용 | 추천 계정 |
|---|---|---|
| 내 연구모임 — 상태 타임라인·다음 할 일 | 단계별로 다른 안내 | 8팀(작성중) → 7팀 → 4팀 → 3팀 → 1팀 순으로 비교 |
| 내 연구모임 — 팀별 최종 일정 | 기획·제작·환류 3단계 일정과 배정 전문가 | 3팀(공개, 대표자가 직접 수정한 이력) / 4팀(**비공개 → 표시 안 됨**) |
| 내 연구모임 — 참여자 명단 수정 | 선발·운영중일 때만 열림 | 3팀·4팀 |
| 배정 팀 확인(전문가) | 배정된 팀·대표자 연락처·코칭 일정 | 한점검(1·4팀), 서점검(2·3팀) / 문점검은 미선정이라 조회 불가 |

### ④ 연구모임 운영 (회의록 `/meetings`, 코칭 조율, 관리자 「연구모임 운영현황」)

| 단계 | 시스템 동작 | 가상자료로 확인 |
|---|---|---|
| 전문가 배정 | 관리자가 팀별 전문가 지정 | 1~4팀 |
| 코칭 일정 조율 | 팀·전문가가 제안 → 가능/불가 회신 → 상대가 확정. 회차당 확정 1건 | 1팀 3회 확정 / 3팀 2차: 13일 **불가**, 14일 **가능** → 대표자가 확정하면 완료 |
| 조율 메모 | 팀·전문가·관리자가 한 스레드에 기록 | 3팀 메모 3건 |
| 회의록 [서식 3] | 운영현황 매트릭스에 n/3으로 집계, 3회 미만 강조 | 1·2팀 3/3, 3팀 2/3 |

### ⑤ 결과보고서 제출·이수확정 (`/report` → 관리자)

| 단계 | 시스템 동작 | 가상자료로 확인 |
|---|---|---|
| [서식 2] 결과보고서 + 산출물 링크 | 상태 **결과보고서 제출**, 이후 수정 불가 | 2팀 |
| 산출물 아카이브 | 유형 필터·CSV, 드라이브 업로드 여부 확인 | 2팀 산출물 드라이브 미업로드 → 보완 요청 대상 |
| 이수확정 | 관리자가 상태를 이수완료로 변경 → 이수확정 메일이 큐에 쌓임 | 1팀 |

### ⑥ 안내 메일 (관리자 「안내 발송」)

메일은 **자동 발송이 아니라 자동 준비 + 관리자 승인**입니다. 상태가 바뀌면 제목·본문이 완성된 행이 큐에 쌓이고,
관리자가 내용을 확인·수정한 뒤 발송합니다. 가상 행 중 `대기` 2건으로 이 화면을 확인하되,
**발송 대신 「취소」로 처리**하십시오(4장 ⑦ 참고).

### ⑦ 관리자 화면별 점검 포인트 (회차 선택 → 「[시스템 점검] …」)

| 관리자 탭 | 확인 내용 |
|---|---|
| 연구모임 관리 | 9팀 상태·점수·순위, 상세 팝업(신청서·계획서 PDF, 윤리 다짐), 워크숍 희망일 집계, 최종 일정 입력(4팀 비공개) |
| 계획서 심사 | 지표별 채점, 심사위원별 제출 현황(6팀 2/3) |
| 연구모임 운영현황 | 전문가 배정, 회의록 n/3, 산출물, 보고서 제출 여부, 코칭 일정 |
| 전문가 신청자 | 선정 2 · 미선정 1, 비전임 표시, 지도 가능 수준 |
| 참여이력 관리 | `[점검 가상자료]` 3건 |
| 안내 발송 | `[점검·가상]` 14건 (성공 12 · 대기 2) |

## 5. 주의사항 (확인된 동작)

| # | 내용 |
|---|---|
| 1 | 가상 팀으로 새 코칭 제안·회신을 저장하면 **표식 없는** 코칭 안내 메일이 큐에 쌓입니다. 수신자는 `@example.com`이므로 「취소」 처리하십시오. |
| 2 | 점검 회차의 신청 마감(7.10.)이 지났으므로 8팀의 계획서 제출·신청서 수정은 **마감 오류**가 납니다. 이는 마감 처리 동작의 정상 시연입니다. |
| 3 | 회의록·결과보고서·코칭 저장은 날짜가 아닌 **상태**(선발·운영중)로 열립니다 → 3팀·4팀으로 시연 가능. 1·2팀은 보고서 제출 후라 잠겨 있습니다. |
| 4 | 점검 회차에서 「심사 확정」을 누르지 마십시오. 운영중 이후 팀(1~3팀)은 순위 계산에서 빠지고 남은 4·5·6·7팀이 선발 규모 4팀 안에 모두 들어, **미선발 5팀과 채점 없는 7팀(0점)까지 선발**로 바뀝니다(로컬 DB 모의 실행으로 확인). 미실행 과제 정리본의 B1·B15와 같은 현상입니다. |
| 5 | 검수 종료 후 반드시 `scripts/reset_system_check_round.sql`로 삭제하십시오. |
