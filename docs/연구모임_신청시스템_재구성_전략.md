# 2026학년도 AI 활용 연구모임 신청시스템 재구성 전략

> 근거문서: [글로컬대학사업] 2026학년도 AI활용 연구모임 운영 계획(안) (´26. 8. 28. / AI융합원)
> 대상 시스템: 「글로컬 AI 동행」 특강 신청·관리 포털 (본 저장소)
> 문서버전 v1.0 · 대상 독자: 개발자 / 운영 관리자
> **예산 항목은 본 전략의 범위에서 제외한다**(운영계획(안) Ⅳ항은 회계 절차로 별도 처리).

---

## Ⅰ. 목적

### 1.1 왜 재구성이 필요한가 — 사업의 성격이 바뀌었다

현행 포털은 **개인이 · 하나의 특강 회차에 · 한 번 신청하고 · 이수하면 끝나는** 1회성 이벤트 신청 시스템이다.
반면 2026학년도 AI 활용 연구모임은 **팀(3~5명)이 · 계획서를 제출해 · 심사로 선발되고 · 6주간 운영하며 · 회의록과 산출물과 결과보고서를 단계마다 제출하는** 다단계 과제관리형 사업이다.

운영계획(안)은 이 사업의 전 주기를 **다섯 번 모두 "시스템"에 위임**하고 있다.

| 운영계획(안)의 5단계 | 문서에 명시된 시스템 역할 |
|---|---|
| ① 연구모임 신청 | "**시스템 접수**" — 3~5명 팀 구성, 신청서·계획서 제출 |
| ② 계획서 심사 | 심사위원 3인 서면심사 (10개 팀 선발) |
| ③ 운영 안내 | "**시스템 안내**" — 승인된 연구모임 활동 안내 |
| ④ 연구모임 운영 | "**시스템을 통한 관리**" — 팀별 퍼실리테이터와 함께 운영 |
| ⑤ 결과보고서 제출 | "**시스템 제출**" — 회의록·산출물·결과보고서 |

즉 시스템은 더 이상 "신청 폼"이 아니라 **사업의 운영 기반(operating backbone)** 이다. 신청 폼만 고쳐서는 사업이 돌아가지 않는다.

### 1.2 재구성의 목적

1. **접수의 목적** — 운영계획(안) [서식 1]의 신청서·계획서를 종이/한글 파일 왕복 없이 시스템에서 직접 작성·제출하게 하여, 담당자의 취합·정리 부담을 없앤다.
2. **심사의 목적** — 9개 지표 100점 만점 심사기준을 시스템에 내장하여, 심사위원 3인의 서면심사가 채점표 배부·회수 없이 이루어지고 총점·순위가 자동 산출되게 한다.
3. **관리의 목적** — 6주간(´26. 9. 28. ~ 11. 11.)의 팀별 활동(회의록·산출물·결과보고서)을 한 곳에 축적하여, 사업 종료 시점에 **자료집·동영상 제작을 위한 원천 데이터가 이미 정리되어 있게** 한다.

### 1.3 재구성의 기본 원칙 — "기존 DB에 추가 탭"

**현행 특강 포털을 폐기·대체하지 않는다.** 현행 시스템은 7~8월 특강 8개 회차의 신청·이수·수료증 데이터를 이미 보유한 운영 자산이며, 심사기준 1번 항목("2025년 AI융합원 프로그램에 참여/이수한 적이 있는가?" 20점)은 **바로 이 데이터를 조회해 채점하는 항목**이다. 두 시스템은 분리되면 안 되고, 오히려 연결되어야 한다.

따라서 재구성 방식은 다음과 같이 확정한다.

> **기존 Supabase 데이터베이스를 그대로 두고, `study_` 접두어를 가진 신규 테이블(= 추가 탭)을 덧붙인다.**
> 기존 10개 테이블(`workshops`, `applications`, `LAWdata`, `certificates`, `admin_users` 외)의 스키마는 **한 컬럼도 변경하지 않는다.**
> 기존 인증(`is_admin()`)·RLS 패턴·Edge Function 본인확인 패턴·CSV 내보내기 유틸리티는 **그대로 재사용**한다.

이 원칙의 실익은 세 가지다.
- **무중단** — 특강 신청·수료증 발급 기능이 재구성 중에도 정상 동작한다.
- **연동** — 심사기준 1번(과거 프로그램 참여·이수 이력)을 `applications` 테이블 조인 한 번으로 자동 채점할 수 있다.
- **저비용** — 관리자 계정·인증·권한 체계를 새로 만들지 않는다. `admin_users` allowlist가 그대로 심사위원·운영자 권한의 기반이 된다.

## Ⅱ. 현행 시스템 진단 (환류)

운영계획(안) Ⅱ항의 환류(재참여 의향 78.1%, 실습시간 확대 및 단계별 매뉴얼 제공 요구)에 더해, **시스템 관점의 환류**를 다음과 같이 정리한다.

### 2.1 그대로 재사용할 자산

| 자산 | 위치 | 연구모임 시스템에서의 역할 |
|---|---|---|
| 구글 OAuth + allowlist 인증 | `src/lib/useAdminSession.ts`, `admin_users` 테이블 | 운영자·**심사위원** 로그인에 그대로 사용 |
| `is_admin()` RLS 헬퍼 | `supabase/migrations/0001_init.sql` | 신규 테이블 RLS 정책에 동일 적용 |
| 익명 INSERT + 관리자 SELECT 패턴 | `applications` RLS 정책 | 신청서·계획서 제출에 동일 적용 |
| 본인확인 Edge Function 패턴 | `supabase/functions/lookup` | **대표자 성명+연락처**로 팀 상태 조회에 재사용 |
| 정원 제어 트리거 + advisory lock | `check_application_capacity()` | **선발 10개팀 정원 제어**에 동일 기법 적용 |
| 폼 프리미티브 | `src/components/ui/FormField.tsx`, `Button.tsx`, `Modal.tsx` | 신규 폼 전부 이 위에 구축 |
| CSV 내보내기(수식 인젝션 방지 + BOM) | `src/lib/csv.ts` | 심사표·팀 명단·산출물 목록 내보내기 |
| 탭 네비게이션 | `PortalTabs.tsx`, `admin/AdminNav.tsx` | 배열 리터럴 1줄 추가로 탭 확장 가능 |
| 정적 export + Edge Function 아키텍처 | `next.config.mjs`, `supabase/functions/` | 서버 없이 동일 방식 유지 |

### 2.2 구조적 격차 — 신규 개발이 필요한 지점

| 축 | 현행 | 연구모임 사업 요구 | 격차 |
|---|---|---|---|
| 신청 단위 | 개인 1행 | **팀 1건 + 참여자 3~5행** | 부모-자식 2단 구조 필요 |
| 신청 산출물 | 정형 6필드 | **정형 필드 + 서술형 계획서 5개 항목** | 장문 텍스트 저장·작성 UI 필요 |
| 선발 방식 | 선착순 정원 | **9개 지표 100점 서면심사 · 상위 10팀** | 심사 테이블·채점 UI·집계 로직 신규 |
| 운영 기간 | 1일(회차) | **6주 · 3차 워크숍(기획→제작→환류)** | 진행단계 상태머신 필요 |
| 제출물 | 없음 | **회의록 · 산출물 링크 · 결과보고서** | 제출 테이블 3종 + 마감 관리 신규 |
| 최종 산출 | 수료증 PDF | 자료집·동영상 원천자료 + 이수혜택(30만 포인트) | 산출물 아카이브·이수확정 기능 신규 |

- PRD.md §13 회차표(5회차·180명)가 실제 구현(8회차·310명)과 어긋나 있다. 연구모임 스펙을 PRD에 추가할 때 **현행 기준으로 함께 갱신**한다.

## Ⅲ. 재구성 전략 개요

### 3.1 이중 트랙(Dual-Track) 구조

하나의 포털이 두 개의 사업 트랙을 나란히 서비스한다.

```
│
└── [트랙 B] AI 활용 연구모임 — 신규 (본 전략의 범위)
    사업안내 · 연구모임 신청 · 연구계획서 · 회의록 · 결과보고서 · 내 연구모임
    DB: study_* 신규 테이블군  ←  "기존 DB에 추가한 탭"
         └ 심사기준 1번 채점 시에만 applications 를 읽기 전용으로 참조
```

### 3.2 5단계 운영흐름 ↔ 탭 매핑

운영계획(안)의 운영개요 5단계를 **그대로 탭 순서로 옮긴다.** 신청자는 탭을 왼쪽에서 오른쪽으로 따라가기만 하면 사업 절차를 완주하게 된다.

```
 ①신청접수      ②계획서심사      ③운영안내      ④연구모임운영      ⑤결과보고서제출
    │                │                │                │                │
 [탭2·탭3]        [관리자탭]       [탭6 알림]        [탭4]            [탭5]
 신청서·계획서     심사·선발       승인결과 안내     회의록 제출     결과보고서·산출물
```

### 3.3 근거문서 페이지 ↔ 탭 확정 매핑

작성원칙에서 지정한 페이지 단위 탭 구성을 다음과 같이 확정한다.

| 근거문서 페이지 | 문서 내용 | 대응 탭 | 성격 |
|---|---|---|---|
| 1~4p (예산 제외) | 목적·환류·운영개요·신청·심사기준·운영·일정·기대효과·향후계획 | **탭 1. 사업안내** | 읽기 전용 안내 |
| 5~6p | [붙임] 교육·연구 및 학생지도 비용 지급 지침 | 탭 1 하단 접이식 섹션 | 읽기 전용 안내 |
| **7p** | **[서식 1] AI 활용 연구모임 신청서** (모임명·주제·대표자·참여인원·참여자 명단) | **탭 2. 연구모임 신청** | 입력 (정형) |
| **8p** | **[서식 1] AI 활용 연구모임 계획서** (작성요령 + 5개 항목 빈 양식) | **탭 3. 연구계획서** | 입력 (서술형) |
| **9~10p** | (계획서 작성 예시) — 중급 RAG 사례 전문 | **탭 3 안에서 흐리게(placeholder) 표시** | 입력 보조 |
| **11~12p** | **[서식 2] 결과보고서** (표지 + 작성방법 + 6개 항목) | **탭 5. 결과보고서** | 입력 (서술형) |
| **13p** | **[서식 3] 회의록** (모임명·일시·장소·주제·토의내용·작성자) | **탭 4. 회의록** | 입력 (반복 제출) |

**8페이지 탭의 "예시 흐리게" 구현 방식**: 9~10페이지 예시 전문을 각 항목 입력란의 **placeholder 텍스트(회색 반투명)** 로 심는다. 사용자가 입력을 시작하면 예시는 자연히 사라지고, 입력값과 절대 섞이지 않는다. 예시 전문을 통으로 보고 싶은 경우를 위해 각 항목 옆에 「작성 예시 보기」 링크를 두어 `Modal`(기존 `src/components/ui/Modal.tsx` 재사용)로 9~10페이지 원문을 띄운다. 예시는 DB에 저장되지 않으며 `src/lib/studyGroupConstants.ts`의 상수로 관리한다.

### 탭 1. 사업안내 — `/study` (공개)

**목적**: 신청 전 사업의 전모를 한 화면에서 파악하게 한다. 현행 소개 탭(`src/app/(portal)/page.tsx`)의 히어로+카드 레이아웃을 그대로 따른다.

**게시 항목 (전부 정적 콘텐츠)**

1. **사업 목적** — (교원) 생성형 AI·AX 도구 수준별 학습으로 AI 활용 교수법·연구 확산 / (학생) 학과·전공을 넘어선 자율 연구공동체 조성, DX와 글로컬 경쟁력 제고
2. **운영개요 5단계 도식** — 신청(시스템 접수) ⇨ 계획서 심사 ⇨ 운영 안내(시스템 안내) ⇨ 연구모임 운영(시스템 관리) ⇨ 결과보고서 제출(시스템 제출). 각 단계 박스가 **해당 탭으로 이동하는 링크**로 동작한다.
3. **신청 안내**
   - 신청기간: **´26. 9. 7.(월) ~ 9. 18.(금)** — 시스템 시각 기준 카운트다운 표시
   - 3~5명 이내 자유 구성, **복수 학과 구성 시 가산점**
   - **비전임 교원 포함 가능**
   - (교원) AI 활용 교수법(연구) 및 **디지털 전환(DX) 관련 주제 필수 선정**
4. **수준별 카테고리 4종** (카드형)

   | 구분 | 카테고리 |
   |---|---|
   | 초급 | 생성형 AI 활용법 탐색과 수업 적용 |
   | 중급 | RAG기반 AI활용 도구 기획·제작 |
   | 고급1 | 바이브코딩 기반 실전 활용 도구 개발 |
   | 고급2 | task 수행 효율화를 위한 AI 에이전트 설계부터 배포까지 |

5. **심사 안내** — 선발 10개팀 최대 50명, 과다 신청 시 AI 전문가 3인 서면심사. **심사기준 9개 지표 100점 만점 표를 신청 전에 공개**한다(신청자가 배점을 알고 계획서를 쓰게 하는 것이 계획서 품질을 올리는 가장 값싼 방법이다).

   | 연번 | 심사기준 | 세부 지표 | 배점 |
   |---|---|---|---|
   | 1 | AI융합원 프로그램 참여 및 이수 | 프로그램 참여 이력 / 이수 이력 | 10 / 10 |
   | 2 | 연구회의 주제 | 연구모임 목적 부합 / AX 역량 향상 기여 | 10 / 10 |
   | 4 | AI 플랫폼 활용 계획 | 카테고리 수준 적절성 / 계획 구체성 / 요청사항 구체성 | 20 / 10 / 10 |
   | 5 | 결과 활용방안 | 미래지향성 / 구체성 | 10 / 10 |
   | | | **총점** | **100** |

## Ⅴ. 백엔드 전략 — 기존 DB에 추가 탭 구성

### 5.1 설계 원칙

1. **기존 10개 테이블 무변경.** `workshops` · `applications` · `LAWdata` · `certificates` · `admin_users` · `kakao_*` · `certificate_templates`의 컬럼·제약·트리거를 건드리지 않는다. 유일한 예외는 `admin_users.role` CHECK 제약에 `'reviewer'` 값을 추가하는 것이며, 이는 기존 행에 영향이 없다.
2. **신규 테이블은 `study_` 접두어**로 네임스페이스를 분리한다. 목록만 봐도 트랙 A/B가 구분된다.
3. **기존 관행을 그대로 따른다** — enum 타입 대신 `text + CHECK`, `uuid` PK + `gen_random_uuid()`, `set_updated_at()` 트리거, `is_admin()` 기반 RLS.
4. **참조는 단방향 읽기 전용.** `study_*` → `applications`는 심사 채점 보조 조회만 하고, `applications` → `study_*` 방향 의존은 만들지 않는다. 트랙 A를 언제든 독립적으로 운영할 수 있어야 한다.

### 5.2 신규 테이블 구성 (9개)

         ├─1 study_group_plans       (계획서, 1:1)
         ├─< study_reviews           (심사, 팀×심사위원)
         ├─< study_meetings          (회의록, 반복)
         ├─1 study_reports           (결과보고서, 1:1)
         ├─< study_outputs           (산출물 링크, 반복)
         └─< study_notifications     (안내 발송 로그)

### 5.3 RLS 정책

전 테이블 `enable row level security`.

> **구현하며 바꾼 점 — 익명 INSERT를 열지 않는다.**
> 특강 신청(`applications`)은 단일 행 폼이라 익명 INSERT(`with check (true)`)를 열어 두었지만,
> 연구모임 신청은 **모임 1건 + 참여자 3~5행 + 계획서 1행을 한 번에 만들고 접수번호를 되돌려줘야**
> 하므로 단일 INSERT로 끝나지 않는다. 게다가 `with check (true)`는 컬럼 값을 제한하지 못해
> `created_by_admin` 위조를 트리거로 따로 막아야 했던 전례(0011)가 있다.
> 그래서 **공개 쓰기를 전부 Edge Function(`study-submit`, service role)으로 모으고
> `study_*`에는 익명 INSERT 정책을 두지 않았다.** 열어 둘 이유가 없고, 닫아 두는 편이
> 컬럼 위조·열거 공격 표면이 작다.

```sql
-- (a) 관리자 전용 접근 — 신청자 경로는 Edge Function이 본인확인 후 대행한다
create policy "study_groups_admin_all" on public.study_groups
  for all using (public.is_admin()) with check (public.is_admin());

-- (b) 관리자 전용 전체 권한 (study_rounds 등)
create policy "study_rounds_admin_all" on public.study_rounds
  for all using (public.is_admin()) with check (public.is_admin());

-- (c) 심사위원 격리 — 자기 채점 행만 접근
create policy "study_reviews_own" on public.study_reviews
  for all using (reviewer_email = (auth.jwt() ->> 'email'))
  with check (reviewer_email = (auth.jwt() ->> 'email'));
create policy "study_reviews_select_superadmin" on public.study_reviews
  for select using (public.is_superadmin());
```

- `study_rounds`만 **익명 SELECT 허용**(`for select using (true)`)한다. 신청기간·카테고리·심사기준을 공개 안내 화면에서 읽어야 하기 때문이며, 개인정보가 없는 메타 테이블이다.
- 신청자의 본인 데이터 조회·수정은 **RLS로 열지 않고 Edge Function을 통한다**(현행 `lookup`과 동일 원칙). SELECT를 닫아두는 편이 열거 공격 표면이 작다.
- **`is_admin()`을 admin/superadmin으로 좁히고 `is_reviewer()`를 신설한다.** 심사위원을 `admin_users`에 `role='reviewer'`로 넣는 것까지는 계획대로지만, `is_admin()`이 reviewer를 포함하면 **심사위원이 기존 특강 신청자(`applications`)의 개인정보까지 보게 된다.** 기존 관리자 행은 role이 admin/superadmin이므로 이 축소로 잃는 권한은 없다. 심사위원은 `is_reviewer()`로 계획서만 읽는다.
- `is_superadmin()` 헬퍼를 동일한 `security definer` 방식으로 신설한다(심사위원은 타인 점수를 못 보고, 총괄 관리자만 전체 집계를 본다).

### 5.4 트리거 · RPC

| 이름 | 종류 | 역할 |
|---|---|---|
| `check_study_group_submit()` | BEFORE INSERT/UPDATE 트리거 | 현행 `check_application_capacity()`를 그대로 본떠 작성. ① `pg_advisory_xact_lock(hashtext('study_round_'‖round_id))` ② 라운드 미존재 → `P0001` ③ **`is_admin()`이면 즉시 통과**(오프라인 소급 등록) ④ 비관리자 INSERT는 `created_by_admin := false` 강제, UPDATE는 기존 값 보존(관리자 등록 표기가 이후 공개 갱신에 지워지지 않게) ⑤ `now() < apply_open_at` → `P0004` ⑥ `now() > apply_close_at` → `P0002` ⑦ `submitted` 전환 시 참여자 수 3~5 검증 → `P0005` ⑧ 접수번호 `SG-{연도}-{학기}-{연번}` 채번(max+1 방식으로 중간 삭제에 내성). 에러코드는 현행 프론트 분기 규약을 그대로 승계 |
| `sync_study_member_count()` | AFTER INSERT/DELETE/UPDATE on members | `member_count` 및 `is_multi_dept` 자동 갱신 |
| `set_updated_at()` | 기존 함수 재사용 | 신규 테이블 전부에 BEFORE UPDATE 부착 |
| `get_study_round_stats()` | RPC (definer, stable, anon 허용) | 라운드별 `{submitted_count, selected_count, remaining_slots}` **집계값만** 익명에 노출. 현행 `get_workshop_availability()`와 동일 설계 |
| `finalize_study_review(p_round_id)` | RPC (definer, admin 전용) | 심사위원 3인 평균 산출 → `total_score`·`rank` 갱신 → 상위 `max_teams` 자동 `selected` 전환. 동점 시 `is_multi_dept` 우선. `pg_advisory_xact_lock`으로 중복 실행 차단 |
| `match_prior_participation(p_name, p_id_number, p_phone)` | RPC (definer, admin 전용) | **기존 `applications` 테이블 조회** — 심사기준 1번용 참여·이수 이력 매칭. 연락처는 숫자만 정규화 비교 |

### 5.5 Edge Function (신규 2개)

현행 3개 함수와 동일한 구조(`Deno.serve` + service role + `_shared/cors.ts` + zod 검증)로 작성한다.

| 함수 | 요청 | 처리 |
|---|---|---|
| `study-lookup` | `{ leaderName, leaderPhone }` | 대표자 성명+연락처 일치 팀만 반환. 연락처는 숫자만 정규화해 하이픈 무관 매칭. 상태·마감일·제출현황·다음 할 일 반환. **불일치는 에러가 아니라 빈 배열**(현행 `lookup` 규약 승계) |
| `study-submit` | `{ kind, ... }` (kind별 판별 유니온) | 공개 쓰기의 **유일한 경로**. `apply`(모임+참여자+계획서 행 생성, 접수번호 반환) / `plan` / `meeting-save` / `meeting-delete` / `report`. `apply`를 제외한 모든 kind는 대표자 성명+연락처 본인확인을 통과해야 하며, **미존재와 불일치를 동일 404 메시지로 통일**해 팀 존재 여부를 노출하지 않는다(현행 `issue-certificate` 규약 승계). 상태 전이 가능 여부를 서버 시각 기준으로 재검증하고, UPDATE에 허용 상태 조건을 다시 걸어 경합에서 안전 실패한다 |

### 5.6 Storage

신규 비공개 버킷 `study-attachments` 1개. 객체 키 규칙 `{group_code}/{kind}/{uuid}.{ext}` (ASCII 한정). 회의록 첨부·산출물 캡처 이미지·제출본 PDF를 저장한다. 접근은 전부 **signed URL(TTL 600초)** 경유하며, 정책은 현행 `certificates` 버킷과 동일하게 `is_admin()` 게이팅 + 신청자용 업로드는 Edge Function이 발급한 `createSignedUploadUrl` 토큰으로 처리한다.

## Ⅶ. 기대효과

**(교원)** 신청부터 결과보고까지 시스템 한 곳에서 진행되어, 한글 서식 파일을 내려받아 작성·이메일 제출하는 왕복이 사라진다. 계획서 작성 시 심사 배점과 작성 예시가 화면에 함께 제시되므로 **계획서 품질 자체가 올라가고**, 이는 곧 사업 성과의 질로 이어진다.

**(운영)** 심사위원 3인의 서면심사가 채점표 배부·회수 없이 이루어지고 총점·순위가 자동 산출된다. 심사기준 1번(과거 프로그램 참여·이수 이력 20점)은 **기존 특강 DB를 조회해 근거가 자동 제시**되므로, 심사위원이 명단을 대조하는 수작업이 사라진다. 워크숍 희망일이 구조화 저장되어 10개 팀의 일정 조율이 교차집계 한 번으로 끝난다.

**(대학)** 6주간 축적된 회의록·산출물 링크·결과보고서가 처음부터 구조화된 형태로 쌓인다. Ⅵ 향후계획의 **"자료집·동영상 제작"과 "공동교육센터 협업, 도내 13개 대학 콘텐츠 제공"** 이 별도 취합 작업 없이 CSV 내보내기로 착수 가능해진다. 차년도 사업은 `study_rounds` 1행 추가만으로 재개된다.
